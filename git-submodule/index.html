GIT SUBMODULE / CONCEPT & WORKFLOW

Git submodule
커밋으로 연결하는 저장소

프로젝트 폴더 안에 다른 Git 저장소를 두고,
상위 저장소가 그 저장소의 특정 커밋을 기록하는 방식입니다. 저장소마다 이력을 유지하면서, 함께 사용할 버전을 고정합니다.

독립된 저장소·이력버전은 커밋 ID로 고정하위 변경 + 상위 참조 변경
MENTAL MODEL

폴더는 안에, 이력은 따로

app/lib/codec는 app 안에 보이지만 codec 자체의 Git 저장소입니다. 상위 커밋 P1은 “codec의 A 커밋을 쓴다”는 참조를 담습니다. codec의 main이 B로 이동해도 P1의 선택은 A로 유지됩니다.

+/−로 확대·축소 · 드래그로 이동 · Ctrl/Cmd + 스크롤로 확대 · 크게 보기 후 Esc로 닫기

위치와 주소

.gitmodules

상위 저장소가 버전 관리하는 설정 파일입니다. 서브모듈의 경로와 clone할 URL 등을 공유합니다.

app/.gitmodules
[submodule "lib/codec"]
    path = lib/codec
    url = https://example.com/team/codec.git

여기에 사용 중인 커밋 ID를 적는 것은 아닙니다.

선택한 버전

gitlink

상위 저장소의 트리에 들어가는 특수 항목입니다. 경로 lib/codec에 사용할 하위 커밋 ID를 기록합니다.

app/ $ git ls-tree HEAD lib/codec
160000 commit a1b2c3d…    lib/codec

160000은 gitlink 모드입니다. 위 커밋 ID는 설명용으로 줄인 값입니다.

왜 사용하나요? 여러 프로젝트가 같은 라이브러리·도구 저장소를 재사용하면서, 각 프로젝트가 검증한 버전을 유지할 때 유용합니다. 대신 clone·동기화·공유 단계에서 두 저장소를 함께 관리해야 합니다.

근거: Git — submodule 구조 · .gitmodules 설정

INTERACTIVE

어느 커밋이 움직일까요?

단계를 눌러 상위의 기록 / 하위의 실제 HEAD / 원격 main을 비교해 보세요. 로컬 변경이 없고, checkout 방식으로 업데이트하는 예제입니다. A와 B는 codec의 서로 다른 커밋입니다.

커밋 포인터 실험A → B / 5 STATES
상위 상태: 깨끗함 · 기록 A = 실제 A
update라는 이름의 두 가지 목적
git submodule update는 상위 index에 기록된 커밋을 재현합니다. --remote를 붙이면 원격 브랜치의 커밋을 선택합니다. 선택한 새 버전을 팀에 반영하려면 상위 저장소에서도 add·commit해야 합니다.

근거: Git — update / --remote / --checkout

SETUP

처음 시작하는 두 가지 상황

예제에서 상위는 app, 하위 경로는 lib/codec입니다. example.com URL은 실제 저장소 주소로 바꾸세요. 각 코드 상단은 실행할 디렉터리입니다.

관리자 · 최초 1회

기존 app에 서브모듈 추가

독립 저장소를 연결하고, 설정 파일과 선택한 커밋을 함께 기록합니다.

app/ 
git submodule add \
  https://example.com/team/codec.git lib/codec
git add .gitmodules lib/codec
git commit -m "Add codec submodule"

추가된 codec에 중첩 서브모듈이 있으면 git submodule update --init --recursive도 실행합니다. 이후 팀 절차에 따라 상위 변경을 공유합니다.

팀원 · 새 환경

이미 연결된 app 내려받기

상위와 중첩 서브모듈을 함께 초기화하고, 기록된 커밋을 체크아웃합니다.

작업 폴더/ 
git clone --recurse-submodules \
  https://example.com/team/app.git app
cd app

이미 일반 clone을 했다면 app 안에서 아래 명령으로 채우면 됩니다.

app/ 
git submodule update --init --recursive

--init: 필요한 서브모듈 등록·초기화 · --recursive: 하위의 서브모듈까지 반복. 근거: Git — clone --recurse-submodules

DAILY WORKFLOW

받아서 쓰기와 버전 올리기

매일 하는 작업은 목적에 따라 갈립니다. 팀이 정한 조합을 받는지, 라이브러리의 새 버전을 채택하는지 먼저 정하면 명령 선택이 쉬워집니다.

A

팀 변경사항 받기 · 기록된 버전 재현

하위 저장소에 새 커밋을 만들 필요가 없습니다. 상위를 갱신한 뒤, 하위를 그 기록에 맞춥니다.

app/ · 로컬 변경부터 확인 
git status
git -C lib/codec status

git pull --ff-only
git submodule update --init --recursive

git submodule status --recursive
git diff --submodule=log

브랜치나 태그를 전환한 뒤에도 update --init --recursive로 하위를 맞춥니다. pull --ff-only가 분기 때문에 멈추면 팀의 merge/rebase 절차로 상위를 정리한 뒤 계속합니다. 기존 로컬 변경은 먼저 commit 또는 stash로 보관하세요.

B

새 버전 채택 · 상위가 가리키는 커밋 변경

codec이 이미 공개한 새 버전을 가져와 검증하고, 상위 저장소에 새 참조를 남깁니다.

app/ · codec의 새 버전 선택 
git submodule update --init --remote --checkout -- lib/codec
git diff --submodule=log
# 프로젝트의 빌드·테스트로 새 조합 검증
git add lib/codec
git diff --cached --submodule=log
git commit -m "Update codec revision"
git push --recurse-submodules=check

--remote는 설정된 원격 브랜치를 fetch하고 그 커밋을 선택합니다. 브랜치 설정이 없으면 원격 HEAD가 가리키는 브랜치를 사용합니다. 위 push는 쓰기 권한이 있는 작업 브랜치에서 실행하는 예제이며, PR 저장소에서는 팀 절차로 공유합니다.

최신 브랜치 대신 특정 릴리스·커밋을 채택하려면?

대상을 직접 체크아웃한 뒤 위와 동일하게 검증하고 상위에서 add·commit합니다. 아래 태그 이름은 예제입니다.

app/ 
git -C lib/codec fetch origin --tags
git -C lib/codec switch --detach v1.2.3
git diff --submodule=log

근거: Pro Git — 하위 원격 변경 반영 · Git — push 시 하위 커밋 검사

AUTHOR WORKFLOW

직접 수정할 때는 두 저장소를 커밋

codec의 코드를 고쳤다면 하위에는 코드 변경을, 상위에는 새 하위 커밋 참조를 남깁니다. 상위에서 git add lib/codec만 해서는 codec 내부 파일의 수정이 커밋되지 않습니다.

codec 저장소코드 수정 → commit → push / PR
→공개 확인
app 저장소통합 검증 → 참조 commit → push / PR
하위 저장소에서

1. 작업 브랜치에 코드 수정 기록

기본 checkout 방식은 하위 커밋을 보통 detached HEAD로 펼칩니다. 수정하기 전 브랜치를 만들어 커밋을 붙잡아 두세요.

app/lib/codec/ 
git switch -c fix/codec-edge-case
# 파일 수정 및 codec 자체 테스트
git add src/codec.c
git commit -m "Fix codec edge case"
git push -u origin fix/codec-edge-case

src/codec.c는 예제 파일명입니다. 실제 수정한 파일을 stage하세요. 원격에 쓰기 권한이 없으면 팀이 접근 가능한 fork와 PR 절차를 사용합니다.

상위 저장소에서

2. 선택한 하위 커밋 참조 기록

codec의 공유할 커밋을 체크아웃한 상태에서 app의 통합 테스트를 거치고 포인터를 저장합니다.

app/ 
git diff --submodule=log
# app의 빌드·통합 테스트
git add lib/codec
git diff --cached --submodule=log
git commit -m "Use fixed codec revision"
git push --recurse-submodules=check

PR 기반 팀이라면 codec PR을 먼저 통합합니다. squash/rebase merge로 커밋 ID가 바뀌면 통합된 최종 커밋을 codec에서 선택한 뒤 app 참조를 기록하세요.

검사는 공개 순서를 보조합니다. --recurse-submodules=check는 변경된 하위 커밋이 하위의 적어도 한 원격에서 확인되지 않으면 상위 push를 중단합니다. 팀과 CI가 그 원격에 접근 가능한지도 확인하세요. on-demand는 필요한 하위 push를 시도하지만, 누락된 commit이나 PR 통합을 대신하지 않습니다.

근거: Pro Git — 하위 저장소에서 작업하기 · Git — check / on-demand

READ THE STATE

상태를 읽으면 다음 동작이 보입니다

git submodule status --recursive는 커밋 상태를, git -C lib/codec status는 하위 파일·브랜치 상태를 확인하는 출발점입니다.

git submodule status 출력의 첫 글자
표시뜻확인할 작업
a1b2c3d… lib/codec
맨 앞 공백		하위 HEAD가 상위 index의 기록과 일치하위 파일이 깨끗한지는 하위 git status로 별도 확인
-a1b2c3d… lib/codec아직 초기화되지 않음update --init --recursive로 초기화
+b7e9f21… lib/codec하위 HEAD와 상위 index에 기록된 커밋이 다름의도한 변경이면 상위 add·commit, 복원이 목적이면 로컬 작업을 보관한 뒤 update
U… lib/codecgitlink가 merge 충돌 상태하위에서 사용할 최종 커밋을 정하고 상위에서 그 참조를 stage

중요: submodule status는 기본적으로 상위 index와 비교합니다. 상위 HEAD 대비 stage한 변경은 git diff --cached --submodule=log로 확인합니다. 근거: Git — submodule status · git status

상위 status에 “modified content” 또는 “untracked content”가 떠요

codec 내부에 커밋하지 않은 파일 변경이나 추적되지 않는 파일이 있습니다. 하위에서 git status와 git diff를 확인하세요. 보존할 수정은 하위에서 commit하거나 stash합니다. 상위 add만으로 내부 수정 파일을 저장할 수는 없습니다.

detached HEAD에서 이미 커밋했어요

그 커밋에 아직 HEAD가 있다면 아래처럼 즉시 브랜치를 만들어 이름을 붙이세요. 이미 다른 곳으로 이동했다면 하위 git reflog에서 커밋 ID를 찾고 git branch rescue/codec-work <커밋ID>로 보존한 뒤 작업을 이어갑니다.

app/ · 하위 HEAD가 작업 커밋에 있을 때 
git -C lib/codec switch -c rescue/codec-work
.gitmodules의 URL이 바뀌었어요

상위 변경을 받은 뒤 로컬 URL 설정을 동기화하고 초기화·업데이트합니다. URL 동기화 자체는 버전을 변경하는 동작이 아닙니다.

app/ 
git submodule sync --recursive
git submodule update --init --recursive
상위 merge 중 서브모듈 참조가 충돌했어요

git ls-files -u -- lib/codec로 충돌 중인 커밋 ID를 확인합니다. codec에서 양쪽 변경을 담을 최종 커밋을 선택하거나 merge해 테스트하고, 새 커밋을 만들었다면 먼저 하위 원격에 공개합니다. 상위에서는 git add lib/codec로 최종 참조를 stage하고 진행 중인 merge를 완료합니다.

--remote가 따라갈 브랜치를 main으로 지정하려면?

아래 설정을 상위에 커밋하면 팀과 공유됩니다. 이 설정은 update --remote의 대상 브랜치를 정합니다. 일반 update가 버전을 자동으로 올리거나, 하위에 로컬 main 브랜치를 만들어 주는 설정은 아닙니다.

app/ 
git submodule set-branch --branch main -- lib/codec
git add .gitmodules
git commit -m "Track codec main for remote updates"
서브모듈을 프로젝트에서 제거하려면?

하위에만 있는 커밋·수정 파일을 먼저 보관한 뒤 실행합니다. 상위의 연결 정보를 제거하고 커밋하는 흐름입니다. Git은 과거 커밋 복원을 위해 로컬 .git/modules/의 데이터를 남길 수 있습니다. deinit만 하면 로컬 등록 해제이므로 프로젝트에서 제거하는 커밋과는 다릅니다.

app/ · 하위 작업 보관 후 
git rm lib/codec
git diff --cached -- .gitmodules lib/codec
git commit -m "Remove codec submodule"
QUICK REFERENCE

목적부터 고르는 명령어

별도 표시가 없으면 상위 저장소 루트에서 실행합니다. 명령은 현재 상태와 팀의 브랜치·PR 절차에 맞춰 사용하세요.

하려는 일명령
처음 clone할 때 하위까지 받기git clone --recurse-submodules <상위URL>
기록된 하위 버전 재현git submodule update --init --recursive
하위 원격의 새 버전 선택git submodule update --init --remote --checkout -- lib/codec
하위 파일·브랜치 상태 확인git -C lib/codec status
아직 stage하지 않은 참조 변화 확인git diff --submodule=log
stage한 참조 변화 확인git diff --cached --submodule=log
새 참조를 상위에 기록git add lib/codec → git commit
하위 커밋 공개 여부 검사 후 상위 pushgit push --recurse-submodules=check
URL 변경을 로컬 설정에 반영git submodule sync --recursive
세 가지만 기억하세요. 기록된 조합을 받을 때는 update. 새 버전을 채택하면 상위 참조를 commit. 직접 수정했다면 하위 커밋을 먼저 공개하고 상위 변경을 공유합니다.
